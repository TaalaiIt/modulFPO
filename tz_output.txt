1. User Story и цель

Решение SmartDev должно принимать подписанные операции от МоегоСклада, безопасно передавать их на локальный кассовый ПК, выполнять фискальную операцию через FiscalConnector и возвращать в МойСклад фискальные реквизиты и печатную форму чека.
2. Границы и роли

Заказчик: ОсОО «Смартдев». Исполнители и согласующие со стороны МоегоСклада и ФПО указываются после назначения.
3. Термины

4. Целевая архитектура

МойСклад обращается только к публичному HTTPS endpointBase SmartDev.
Fiscal Agent устанавливает исходящее защищённое соединение с Gateway; входящий проброс портов на кассу не требуется.
FiscalConnector остаётся доступным только локально; публикация localhost:8080 в интернет запрещена.
Gateway использует JSON API 1.2 как вспомогательный канал для настроек, сверки и получения разрешённых сущностей; основной запуск фискализации выполняется через Fiscal API 1.0.
4.1. Архитектурный принцип: универсальное ядро + адаптер поставщика
Модуль разрабатывается как универсальная платформа SmartDev FPO Integration. МойСклад является первым поставщиком входящих операций, но не должен быть зашит в бизнес-логику ядра.
В Integration Core запрещены прямые ссылки на X-Lognex-Fiscal-*, Vendor API, meta.id, retailStore.id, access_token, endpointBase МоегоСклада и формат receipt PDF/ZIP/Base64. Эти элементы принадлежат только Provider Adapter MOYSKLAD.
4.2. Контракт Provider Adapter
Каждый новый поставщик реализует один и тот же логический контракт. При добавлении 1С, Frontol, Paloma или другого источника заменяется только каталог providers/<providerCode>/.
4.3. Нормализованная модель операции Core
Идемпотентность Core строится по providerCode + providerAccountId + operationType + externalOperationId. Для МоегоСклада это эквивалентно текущей логике account + operationType + meta.id, но ядро не знает названия meta.id.
4.4. Поля, которые разрешено менять при подключении другого провайдера
Все поля ФПО КР (registrationNumber, fmNumber, fdNumber, fiscalMark, VAT/ST, calcItemAttributeCode, measure, SGTIN, state-shift, 40417, 4011) относятся не к МоемуСкладу, а к FPO Adapter и остаются общими для всех провайдеров.
5. Контракты интеграции
5.1. Установка серверного решения SmartDev
SmartDev получает доступ к личному кабинету разработчика МоегоСклада и создаёт черновик серверного решения.
В дескрипторе указываются блоки vendorApi, fiscalApi и доступ к JSON API 1.2; в fiscalApi задаются endpointBase, operationTypes и paymentTypes.
При установке МойСклад вызывает Vendor API SmartDev и передаёт access_token JSON API, а также additional.fiscalApi.id и additional.fiscalApi.token (публичный RSA-ключ).
SmartDev сохраняет установку по accountId, проверяет её статус и возвращает Activated либо SettingsRequired.
Настройка решения выполняется в главном окне внутри МоегоСклада: точка продаж, локальный агент, РНМ, принтер и разрешённые способы оплаты.
В точке продаж выбираются облачное формирование чеков и решение SmartDev; затем устанавливается и синхронизируется Касса МойСклад.

5.2. Операции Fiscal API 1.0


5.3. JSON API 1.2
Доступ выполняется только по токену, полученному через Vendor API: Authorization: Bearer <access_token>.
Запрашивать у клиента логин и пароль МоегоСклада для интеграции запрещено.
JSON API используется для получения разрешённых данных точки продаж, смены, сотрудника, продажи, возврата, товара, единицы измерения и дополнительных полей.
Ссылки meta.href из Fiscal API могут использоваться для адресного чтения; массовое повторное чтение всех сущностей не допускается без необходимости.
При удалении или приостановке решения токен считается недействительным и должен быть удалён из активной конфигурации SmartDev.

6. Функциональные требования
6.1. Настройка кассы и агента
Fiscal Agent устанавливается на каждый кассовый ПК, запускается как служба и автоматически восстанавливает исходящее соединение.
Привязка агента к точке продаж выполняется одноразовым кодом без передачи PIN и пароля ФПО в интерфейс МоегоСклада.
Для точки сохраняются accountId, retailStore.id, идентификатор агента, РНМ, выбранный кардридер, формат бумаги и допустимые способы оплаты.
Логин/пароль ФПО и PIN SAM-карты хранятся локально в защищённом хранилище ОС; в центральных логах значения маскируются.
Перед активацией кассы выполняется диагностика: доступность агента, FiscalConnector, кардридера, SAM-карты и соответствие РНМ.
6.2. Преобразование данных продажи


6.3. Налоги и дополнительные поля
Fiscal API передаёт НДС, но исходный контракт ФПО дополнительно требует ставку НСП (st) и calcItemAttributeCode.
При установке решения допускается создать через JSON API дополнительные поля товара: «Код предмета расчёта ФПО» и «Ставка НСП ФПО», если такой подход согласован с МоимСкладом.
Не допускается автоматически подставлять налоговую ставку или признак предмета расчёта без подтверждённого правила.
Поддерживаемые значения исходного ФПО: VAT_0, VAT_12 и ST_0, ST_1, ST_2, ST_3, ST_5; фактический справочник нужно получать из /driver/cash-register/available-tax-rates.
6.4. Ответ Fiscal API и печатная форма
Успешный ответ содержит fnNumber, kktRegNumber, fiscalDocNumber, fiscalDocSign, time и, для смены, shiftNumber; закрытие смены также содержит chequesTotal и fiscalDocsTotal.
Поле receipt формируется как PDF, упакованный в ZIP и переданный Base64-строкой согласно сценарию Fiscal API.
Поддерживаемые форматы печати: 56 мм, 80 мм и А4; формат выбирается в настройках точки продаж.
Печатная форма включает обязательные реквизиты ФПО, QR-код не менее 20 x 20 мм, данные организации, адрес, налоги, оплаты и позиции.
Повторная печать использует ранее сохранённый receipt и не создаёт новый фискальный документ.
6.5. Идемпотентность и повторные запросы
Ключ операции: X-Lognex-Fiscal-Account-Id + тип операции + meta.id (для смены - retailShift.meta.id и тип события).
Повтор идентичного запроса после успешной фискализации возвращает сохранённый результат без повторного вызова ФПО.
Повтор с тем же ключом и изменённым телом отклоняется как конфликт данных.
До отправки в ФПО безопасный повтор разрешён. После отправки и потери ответа операция переводится в UNKNOWN и не повторяется вслепую.
Для выхода из UNKNOWN требуется штатный поиск/сверка фискального документа либо ручное подтверждение; этот механизм должен быть согласован с поставщиком ФПО.
6.6. Ошибки и автоматическое восстановление


6.7. Контроль лицензии модуля SmartDev
Лицензирование является отдельной подсистемой SmartDev и не должно зависеть от МоегоСклада. Установка решения в МойСклад, наличие access_token или статус Vendor API не являются лицензией SmartDev.
За основу используется схема SmartMag: код активации -> привязка к hardwareId -> выдача license_key/device_token -> проверка при запуске и периодически -> heartbeat -> локальный кэш разрешения -> ограниченное офлайн-окно.
6.8. Привязки лицензии
Ключевой принцип: providerAccountId нельзя использовать как единственный идентификатор лицензии. Лицензия принадлежит SmartDev-модулю, Seat принадлежит устройству/агенту, а Provider Binding можно заменить при подключении другой системы.
6.9. API лицензирования SmartDev
Успешная register-операция должна возвращать license_key, device_token и entitlements. device_token хранится локально в защищённом хранилище и используется для следующих проверок.
6.10. Правила блокировки лицензии
Перед каждой новой фискальной операцией Gateway проверяет активное entitlement в локальном/серверном кэше.
Если active=false, paid=false, blocked=true или срок лицензии истёк — новая операция не отправляется в ФПО.
Если HWID не совпадает — Agent получает HARDWARE_MISMATCH и не принимает новые фискальные команды до rebind.
Если providerCode/providerAccountId не разрешён — Gateway возвращает PROVIDER_BINDING_MISMATCH до обращения к Agent.
Если РНМ не соответствует активному FPO Binding — операция блокируется до подтверждённой перепривязки.
Если SmartDev License Service временно недоступен, разрешается работа по последнему успешному кэшу в пределах offlineLimitHours; по умолчанию 24 часа.
Если фискальная операция уже была отправлена в FiscalConnector, изменение статуса лицензии не должно обрывать обработку. Сначала операция доводится до безопасного результата/UNKNOWN; блокируются только следующие операции.
Лицензионная ошибка никогда не должна приводить к автоматическому повторному вызову FiscalConnector.
7. Ограничения
Валюта фискальных операций - KGS.
Максимальная длительность смены ФПО - 24 часа.
Для авторизации и открытия смены ФПО требуется интернет; после получения accessToken смена должна быть открыта в течение 5 минут.
Несмотря на локальные офлайн-возможности ФПО, стандартная связка с облачной Кассой МойСклад требует доступности интернета для вызова Fiscal API.
Произвольный возврат без продажи-основания в текущем объёме запрещён.
Покупка (EXPENDITURE) и возврат покупки (EXPENDITURE_RETURN) не входят в стандартный набор операций Fiscal API 1.0 и находятся вне объёма.
X-отчёт не имеет стандартного endpoint в Fiscal API 1.0 и реализуется только как локальная функция SmartDev.
Отдельное поле округления наличной суммы отсутствует в исходном контракте ФПО; правило округления требует согласования.
8. Use Cases

UC-01. Установка и настройка решения
Предусловие: Администратор имеет аккаунт МойСклад и права установки решений.
Администратор устанавливает решение SmartDev из каталога или по прямой ссылке.
МойСклад вызывает Vendor API SmartDev и передаёт токен JSON API и данные fiscalApi.
SmartDev возвращает SettingsRequired и открывает встроенное окно настройки.
Администратор выбирает точку продаж и получает одноразовый код привязки агента.
Fiscal Agent активируется на кассе, проверяет FiscalConnector, кардридер и SAM-карту.
SmartDev завершает настройку и переводит решение в Activated.
В точке продаж выбирается облачное формирование чеков и решение SmartDev.

UC-02. Успешное открытие смены
Предусловие: Интернет доступен; агент онлайн; SAM-карта вставлена.
Кассир открывает смену в Кассе МойСклад.
МойСклад отправляет PUT /1/openshift с подписью и идентификатором установки.
Gateway проверяет подпись, tenant и идемпотентность, затем направляет команду агенту.
Агент выполняет GET /driver/sam-cards и при необходимости POST /driver/verify-pin.
Агент выполняет POST /driver/auth, затем GET /driver/state-shift.
Если смена закрыта, агент выполняет POST /driver/open-shift.
Gateway формирует PDF-чек открытия, ZIP/Base64 и возвращает фискальные реквизиты.
Касса печатает документ открытия смены.

UC-03. SAM-карта отсутствует
Предусловие: Кардридер подключён, SAM-карта не вставлена.
Кассир инициирует открытие смены.
Агент выполняет GET /driver/sam-cards и получает cardPresent = false.
Gateway не выполняет auth и open-shift.
В МойСклад возвращается блокирующая ошибка с рекомендацией вставить SAM-карту и повторить.

UC-04. Нет интернета при открытии смены
Предусловие: SAM-карта вставлена; доступ к серверу ГНС или Gateway отсутствует.
Кассир инициирует открытие смены.
Если Gateway недоступен, Касса МойСклад показывает ошибку внешнего решения.
Если Gateway доступен, но POST /driver/auth не может связаться с ГНС, агент возвращает ошибку соединения.
Повтор разрешается только после восстановления связи.

UC-05. Продажа за наличные
Предусловие: Смена открыта; данные товара и налоги заполнены.
Кассир добавляет товар и принимает наличную оплату.
МойСклад отправляет POST /1/retaildemand.
Gateway валидирует позицию, суммы и ключ идемпотентности.
Агент выполняет GET /driver/state-shift, затем POST /driver/cash-register/receipt с operationType = INCOME.
В ФПО передаются totalCashSum, totalCashlessSum = 0, позиции, налоги и маркировка.
Gateway возвращает фискальные реквизиты и receipt; Касса печатает чек.

UC-06. Продажа банковской картой
Предусловие: Смена открыта; эквайринговая оплата подтверждена.
Кассир закрывает продажу с оплатой картой.
МойСклад отправляет cardSum в POST /1/retaildemand.
SmartDev преобразует сумму в totalCashlessSum и выполняет фискализацию INCOME.
После успешного ответа формируется и печатается чек.

UC-07. Смешанная оплата наличными, картой или QR
Предусловие: Смена открыта; выбранный paymentType разрешён дескриптором решения.
Покупатель оплачивает чек несколькими способами.
МойСклад передаёт cashSum, cardSum и/или qrSum.
SmartDev рассчитывает totalCashSum и totalCashlessSum, проверяет равенство итоговой сумме.
Агент отправляет один фискальный чек INCOME.
Gateway сохраняет детализацию оплаты и возвращает единый receipt.


UC-08. Возврат продажи
Предусловие: Смена открыта; исходная продажа успешно фискализирована и сохранена.
Кассир выбирает возврат на основании продажи МойСклад.
МойСклад отправляет запрос возврата с demand.meta исходной продажи.
Gateway находит сохранённые originFdNumber и originFnSerialNumber исходного чека.
Агент выполняет POST /driver/cash-register/receipt с operationType = INCOME_RETURN и возвращаемыми позициями.
Gateway сохраняет результат и возвращает чек возврата.

UC-09. Внесение наличных
Предусловие: Смена открыта; операция включена в operationTypes.
Кассир создаёт внесение в Кассе МойСклад.
МойСклад отправляет POST /1/retaildrawercashin.
SmartDev конвертирует sum в KGS и вызывает POST /driver/cash-transaction/deposit.
Gateway возвращает фискальные реквизиты и чек внесения.

UC-10. Выплата (изъятие) наличных
Предусловие: Смена открыта; в кассе есть достаточная сумма.
Кассир создаёт выплату в Кассе МойСклад.
МойСклад отправляет POST /1/retaildrawercashout.
SmartDev вызывает POST /driver/cash-transaction/withdraw.
Gateway возвращает фискальные реквизиты и чек выплаты.

UC-11. X-отчёт
Предусловие: Смена открыта; локальный агент доступен.
Пользователь открывает локальную диагностику SmartDev и выбирает X-отчёт.
Agent выполняет GET /driver/x-report.
Отчёт отображается или печатается локально без закрытия смены.


UC-12. Успешное закрытие смены
Предусловие: Смена открыта; остаток наличных ФПО равен нулю.
Кассир закрывает смену в Кассе МойСклад.
МойСклад отправляет PUT /1/closeshift.
Агент проверяет остаток через GET /driver/cash-transaction.
При нулевом остатке агент выполняет POST /driver/close-shift.
Gateway возвращает Z-отчёт, shiftNumber, ФПД, chequesTotal и fiscalDocsTotal.
Касса печатает документ закрытия смены.

UC-13. Закрытие смены при ненулевом остатке
Предусловие: Смена открыта; в кассе остались наличные.
Кассир инициирует закрытие смены.
Агент определяет ненулевой остаток либо получает ошибку ФПО 40919.
Gateway возвращает блокирующее сообщение о необходимости изъятия.
Кассир выполняет выплату и повторяет закрытие.

UC-14. Недоступность ФПО до отправки документа
Предусловие: Кассир завершает чек; Agent или FiscalConnector не отвечает.
Gateway проверяет присутствие онлайн-агента.
Агент выполняет GET /driver/state-shift.
При таймауте до вызова cash-register/receipt документ в ФПО не отправляется.
МойСклад получает ошибку связи; пользователь может повторить после восстановления.

UC-15. Таймаут после отправки документа в ФПО
Предусловие: GET state-shift успешен; запрос receipt отправлен, но ответ потерян.
Agent фиксирует момент отправки и переводит операцию в PROCESSING.
При таймауте Gateway устанавливает статус UNKNOWN.
Повторный запрос МоегоСклада с тем же meta.id не отправляется в ФПО повторно.
SmartDev выполняет штатную сверку результата или требует ручного решения уполномоченного пользователя.
После подтверждения найденный результат возвращается при следующем повторе.


UC-16. Автоматическая обработка 40417 NOT_VERIFY_PIN
Предусловие: Смена открыта; SAM-карта была переустановлена или потеряла верификацию.
ФПО возвращает код 40417 на фискальной операции.
Agent один раз вызывает POST /driver/verify-pin с локально сохранёнными РНМ и PIN.
При успехе Agent автоматически повторяет исходную операцию с тем же ключом.
При ошибке verify-pin Gateway возвращает блокирующее сообщение.

UC-17. Автоматическая повторная авторизация 4011
Предусловие: ФПО требует повторную авторизацию.
ФПО возвращает 4011 REAUTHORIZATION_REQUIRED.
Agent один раз выполняет POST /driver/auth и получает новый accessToken.
Agent повторяет исходную операцию с тем же ключом идемпотентности.
При повторной ошибке Gateway прекращает автоматические попытки.

UC-18. Повтор идентичного запроса МоегоСклада
Предусловие: Операция уже успешно фискализирована, но МойСклад повторил HTTP-запрос.
Gateway вычисляет ключ account + operationType + meta.id.
Gateway находит сохранённый успешный результат и сверяет хэш тела.
FiscalConnector повторно не вызывается.
В МойСклад возвращается исходный набор реквизитов и тот же receipt.

UC-19. Активация лицензии модуля
Предусловие: В SmartDev CRM создана активная лицензия FPO_INTEGRATION и выдан activationCode.
Администратор устанавливает Fiscal Agent и выполняет привязку к установке Provider Adapter.
Agent формирует устойчивый hardwareId и собственный agentId.
Agent/Gateway вызывает POST /api/v1/module/register с activationCode, moduleCode, agentId, hardwareId и providerCode=MOYSKLAD.
License Service проверяет active/paid/blocked, лимит maxAgents и создаёт Seat.
В ответ возвращаются license_key, device_token и entitlements.
Agent сохраняет device_token локально и выполняет диагностику FiscalConnector/SAM/РНМ.
Ожидаемый результат: лицензированный Agent готов принимать команды; в CRM видны HWID, agentId, Provider Binding и РНМ.
UC-20. License Service временно недоступен
Предусловие: Лицензия ранее успешно проверена; lastLicenseOk находится внутри offlineLimitHours.
Agent не получает ответ SmartDev License Service.
Agent проверяет защищённый локальный кэш последней успешной лицензии.
Если grace не истёк, работа продолжается; событие пишется в аудит как LICENSE_GRACE.
После восстановления связи heartbeat обновляет состояние и lastLicenseOk.
Ожидаемый результат: временная недоступность CRM не останавливает кассу в пределах разрешённого окна.
UC-21. Лицензия заблокирована или не оплачена
Предусловие: License Service возвращает blocked=true либо paid=false/active=false.
Gateway завершает уже отправленные в ФПО операции до безопасного статуса.
Все новые операции блокируются до обращения к FiscalConnector.
Provider Adapter возвращает понятную ошибку внешней системе и код LICENSE_BLOCKED/NOT_PAID.
После восстановления лицензии новая проверка/heartbeat возвращает работу без переустановки Provider Adapter.
Ожидаемый результат: нет новой фискализации при неактивной лицензии и нет повреждения уже начатой операции.
UC-22. Изменение оборудования
Предусловие: Лицензия активна, но текущий hardwareId отличается от Seat.
Agent обнаруживает HWID mismatch до подключения рабочего канала.
License Service возвращает HARDWARE_MISMATCH.
Фискальные команды блокируются.
Уполномоченный сотрудник SmartDev выполняет rebind или выдаёт новый activationCode.
После rebind Agent получает/обновляет device_token и повторно проходит диагностику.
Ожидаемый результат: копирование установленного Agent на другой ПК не даёт доступ к лицензии.
UC-23. Смена внешней системы без переписывания Core
Предусловие: Core, Agent, FPO Adapter и License Service работают; требуется подключить нового провайдера.
Разработчик создаёт providers/<newProviderCode>/ и реализует Provider Adapter contract.
Новый адаптер преобразует внешние операции в NormalizedFiscalOperation.
В CRM лицензии добавляется newProviderCode в allowedProviders.
Создаётся новый Provider Binding без изменения Seat/HWID и FPO Adapter, если используется та же касса/РНМ.
Core выполняет те же SALE/RETURN/SHIFT операции без изменений.
Ожидаемый результат: добавление новой внешней системы не требует изменения фискального ядра и лицензирования.
9. Критерии приёмки
Решение устанавливается и удаляется через Vendor API; токены корректно активируются и отзываются.
Все запросы Fiscal API с неверной подписью или неизвестным accountId отклоняются.
Открытие, продажа, возврат, внесение, выплата и закрытие смены проходят по согласованным endpoint.
Наличные, карта, QR и смешанная оплата корректно преобразуются в суммы ФПО.
НДС, НСП, единица измерения, calcItemAttributeCode и маркировка валидируются до обращения к ФПО.
Повтор одного meta.id не создаёт второй фискальный документ.
40417 и 4011 автоматически обрабатываются не более одного раза.
Таймаут после отправки не приводит к слепому повтору; доступна процедура сверки UNKNOWN.
PDF-чек в ZIP/Base64 печатается на 56 и 80 мм; QR-код читается сканером.
Секреты и персональные данные отсутствуют в открытых логах; localhost:8080 не доступен извне.
Журнал аудита связывает accountId, meta.id, retailStore.id, агент, запрос, результат и фискальные реквизиты.
9.1. Дополнительные критерии универсальности и лицензирования
В исходном коде Integration Core отсутствуют строки X-Lognex-*, meta.id, retailStore.id и URL МоегоСклада; они находятся только в providers/moysklad.
Core принимает и обрабатывает NormalizedFiscalOperation одинаково для MOYSKLAD и тестового MockProvider.
Добавление MockProvider проходит без изменения файлов core/, fpo/, licensing/ и agent/.
Лицензия активируется по activationCode и создаёт Seat с agentId + hardwareId.
При повторном запуске на том же HWID код активации повторно не запрашивается, пока лицензия разрешена.
Копирование Agent на другой HWID не даёт выполнить фискальную операцию без rebind.
blocked=true, paid=false или active=false блокируют новые операции до вызова FiscalConnector.
Недоступность License Service допускает работу не более offlineLimitHours с момента последней успешной проверки.
Provider Binding для MOYSKLAD хранится отдельно от Seat и может быть заменён на другой providerCode без изменения лицензирующего клиента.
allowedProviders и maxAgents/maxRnms контролируются на сервере SmartDev, а не только в UI Agent.
Изменение лицензии во время PROCESSING не прерывает уже отправленную в ФПО операцию и не создаёт дубль.
